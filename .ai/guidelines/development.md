# Local Development

- Lock is a full **Laravel 13 + Inertia + React + Lattice** application (Lattice provides server-driven UI). It is
  served locally with **Herd** at `http://lock.test`. PHP `^8.5`.
- First-time setup: `composer setup` installs dependencies and calls `app:setup`, which generates missing local keys
  and console credentials, then runs `app:deploy`. Repeating it preserves existing credentials. `composer fresh`
  resets the local database, runs setup, then seeds the non-admin demo user. `db:seed` adds demo data only and
  never writes environment files. Day-to-day, `composer dev` runs the queue, Pail and Vite; Herd serves HTTP.
- Data changes and backfills live in `database/data-migrations/`, not in the schema-only `database/migrations/` (see
  `.ai/rules/data-migrations.md`). They run through the normal Migrator on a separate path; on a deploy
  `php artisan app:deploy` runs them as its own step after `php artisan migrate`. `composer setup`,
  `bin/create-worktree.sh`, `composer fresh`, and `Tests\TestCase` all already run
  the folder.
- **Deploys run one command: `php artisan app:deploy`.** It runs `migrate --force`, the data migrations,
  `oidc:rotate-keys --if-missing` for every realm (signing keys live in `oidc_signing_keys`, one keypair per realm,
  and the data migrations create the master realm the first deploy needs one for), `app:bootstrap` (reconciles the
  management API resource and its scopes, the protected `Super Admin`/`Support` roles from
  `App\Admin\ManagementRoles`, the console client and the first administrator), and `lattice:discover-cache`. Every step is
  idempotent. A database advisory lock (PostgreSQL/MySQL) or SQLite file lock protects the entire workflow;
  a concurrent deploy fails before doing any work and must be retried. Bytecode caches
  (`config:cache`, routes, views) stay with the deploy platform. Grant the first admin with
  `php artisan admin:grant {email}` (revoke by clearing the user's master realm roles in the admin UI).
- The frontend is **not** an Inertia-React `resources/js/Pages` app. Pages, forms, tables, and actions are PHP classes
  (`#[AsPage]`, `#[AsForm]`, `#[AsTable]`, `#[AsAction]`) rendered by the Lattice runtime. The only hand-written React
  lives in `resources/js/` (the `registry.ts` plugin and a few custom components registered by string key). Prefer the
  `lattice-actions`, `lattice-forms`, and `lattice-tables` skills when building UI.
- After changing a custom Lattice wire type (a `#[AsComponent]`/`#[AsField]`/`#[AsColumn]` class such as
  a custom component or column class), regenerate its TypeScript with `php artisan lattice:typescript`
  (committed to `resources/js/lattice/generated.d.ts`; needs the `spatie/laravel-typescript-transformer` dev dep).
- Path-scoped conventions live in `.ai/rules/` — `index.md` maps globs to rule files. Read the rules matching the
  paths you are about to touch before planning or editing, and record a durable new one there rather than in a
  session note.
- `@laravel/passkeys` in `package.json` has no app-side import but must stay: the use-lock/server package’s integrated UI's passkey
  components import `@laravel/passkeys/react` without declaring it as their own dependency.
- Regenerate `CLAUDE.md` and `AGENTS.md` after editing files in `.ai/guidelines/` with `php artisan boost:update`
  (both files are git-ignored and generated by Laravel Boost). `composer post-update-cmd` runs `boost:update`
  automatically after `composer update`.

## Verification

- Git hooks enforce the local gate automatically. `composer install` and `composer update` point `core.hooksPath` at
  `.githooks`; if hooks are not active, run `composer hooks:install` once.
- **pre-commit** auto-formats staged PHP, TypeScript, and Markdown with Pint, oxfmt, and oxlint, re-stages fixes, and
  blocks on remaining lint errors.
- **pre-push** runs the full local gate, scoped to what the push actually touches: the frontend checks, then
  `vendor/bin/phpstan analyse`, `composer rector:check`, `composer test`, and `npm run build`.
- Backend gate: **`composer test`** — clears config, runs Pint in check mode (`pint --parallel --test`), then
  `php artisan test`.
- Static analysis: **`vendor/bin/phpstan analyse`** (Larastan). Keep it at zero errors.
- Automated refactoring: **`composer rector:check`** (dry run) and `composer rector:fix` to apply. Both the `php-static`
  CI job and pre-push run the check, so a pending Rector change fails the build rather than sitting unnoticed.
- Frontend: `npm run lint:check` (oxlint), `npm run format:check` (oxfmt), `npm run types:check` (`tsc --noEmit`),
  and `npm run build` (Vite). Use `npm run lint` / `npm run format` to auto-fix.
- oxfmt formats Markdown as well as TypeScript, so every `.md` in the repo is gated by `npm run format:check`. Write
  globs and other `*`-bearing literals as code spans: oxfmt reads a bare `*` as emphasis and rewrites
  `app/*/Concerns/**` into `app/_/Concerns/\**`. `.ai/rules/index.md` is exempt via `.prettierignore` because its
  whole payload is such a table.
- CI mirror: **`composer ci:check`** runs `npm run lint:check`, `npm run format:check`, `npm run types:check`,
  `vendor/bin/phpstan analyse`, `composer rector:check`, then `composer test`. For a full local pass on a change
  touching both stacks: `composer check:full` includes all checks, the build and browser tests. Never push on red. Use `git commit --no-verify` or
  `git push --no-verify` only in emergencies.

## Comments

- Code must be self-explanatory: reach for clear names, small functions, and types before a comment.
- Do not add comments. A comment is a last resort and explains only _why_ something is done, never _what_ the code does.
- When you encounter an obsolete, redundant, or "what" comment, delete it.
- Delete section banners and navigation comments unless they explain a non-obvious boundary.
- Delete comments that narrate the next line, assertion, or obvious test setup; prefer clearer test names and variable names.
- Keep PHPDoc/JSDoc only when it carries type information, public API intent, static-analysis value, generated-file context,
  or a non-obvious constraint.
- Keep comments that explain framework quirks, ordering requirements, browser/test timing, cache/build behavior, performance
  traps, or other constraints that are hard to infer from the code alone.

## Running tests

- Tests are **Pest**, in three suites: `tests/Unit`, `tests/Feature`, and `tests/Browser`. `php artisan test` runs all
  three; filter with `--filter` or a path, and prefer `--compact`.
- Browser tests drive a real headless Chromium via `pestphp/pest-plugin-browser` (Playwright). They need the browsers
  installed once (`npx playwright install`), the app reachable at `lock.test` (Herd), and a current
  `npm run build` — they serve the built bundle, not the dev server.
- How to _write_ a test — suite choice, the Lattice helpers, fixtures, and the bar a test has to clear — lives in
  `.ai/rules/testing.md`.
